# Git / Branch・Fork / 必要時の運用

## 保存の対応表

| ゲーム感覚 | Git | 意味 |
| --- | --- | --- |
| セーブスロット | Branch | 作業目的ごとに分けたルート |
| セーブした瞬間 | Commit | 単独で意味を持つ小さな変更 |
| セーブ内容のメモ | Commit message | 何を変えたかの説明 |
| セーブから再開 | `git switch` | そのBranchへ移動 |
| 本編へ採用 | Merge | 検証済み変更をmainへ統合 |
| 一部だけ採用 | cherry-pick | 特定Commitだけを複製 |

原本: [保存と分岐の説明](./原本チャット_保管.md#ゲームのセーブとの対応)

## Branchを使う時

自分のリポジトリで、機能追加・修正・試作を分けたい時に使う。

```text
main                     動く原本・公開候補
feature/battle-ui        バトルUIの作業
feature/save-system      セーブ機能の作業
experiment/ai-enemy      敵AIの実験
```

### 作る判断

- 本体に影響する変更が複数日にまたがる。
- 試作が失敗する可能性が高い。
- 他の作業と混ぜるとレビューや撤回が難しい。
- 並行で別目的の作業を進める。

### 作らない判断

- 文言、CSS、単独の小修正だけ。
- 変更目的が一つで、短時間に検証できる。
- まだ実験の目的が決まっていない。

## Forkを使う時

他人のリポジトリを自分のGitHub管理下へ複製し、独自修正や本家への提案を行う時に使う。

```text
upstream/main             原作者の原本
origin/main               自分のFork
fix/poison-timing         自分のFork内の作業Branch
```

外部OSSを読むだけ、依存として使うだけならForkしない。元ライブラリへ修正を提案したい、または長期間独自改造する時に使う。

原本: [Forkの例](./原本チャット_保管.md#フォークを使う例)

## mainへ入れるルール

次を満たした変更だけ、PRを通してmainへ統合する。

```text
起動できる
+ 既存機能が壊れていない
+ 変更目的を一文で説明できる
+ 戻したくなった時に原因を追える
= mainへマージ可能
```

UIが未完成でも、機能として価値が成立し、仕様が決まり、検証できているなら採用候補になる。デバッグコードや仮素材は分離または削除してから統合する。

原本: [マージのルール](./原本チャット_保管.md#マージのルール)

## 一部だけ採用する時

複数Commitのうち、完成しているものだけをmainへ持ち帰る。

```bash
git switch main
git cherry-pick <commit-A>
git cherry-pick <commit-B>
```

このため、Commitは「HPバーの枠」「HP値表示」「ダメージ演出」のように小さく区切る。

原本: [cherry-pick](./原本チャット_保管.md#部分反映)

## Codexとの境界

この資料は、Codexに「常にBranchを作る」と命令するものではない。

- ユーザーがBranch/Forkを指定した時は、その目的に沿って操作する。
- 変更の隔離が安全性に明確に役立つ時は、Codexが提案することはある。
- 実際の作成・マージ・cherry-pickは、対象リポジトリと変更範囲を確認してから行う。
- `main`を直接壊す操作、履歴を書き換える操作は、明確な依頼なしにしない。
