# Git / Branch・Fork / 原本チャット保管

> 状態: 学習用原本。

## 統合と部分反映

成功した変更を原本へ戻す基本は Pull Request -> Merge。

必要な変更だけ選ぶなら cherry-pick を使う。

```text
main（原本）
└ feature/battle-ui（作業）
  ├ commit A: HPバー追加
  ├ commit B: 演出追加
  └ commit C: 未完成の設定画面
```

HPバーと演出だけ成功なら、通常は `feature/battle-ui` からmainへPRを作り、確認してマージする。

「AとBだけ入れたい。Cはまだ入れない」なら、main側でA/BのCommitだけを取り込む。

```bash
git switch main
git cherry-pick <commit-AのID>
git cherry-pick <commit-BのID>
```

## 他人のリポジトリをフォークした場合

```text
原作者: upstream/main
            ↓ 定期同期
自分: origin/main
            ↓ 作業
      feature/my-fix
```

原作者の更新を自分のForkへ取り込む操作は同期。

```bash
git fetch upstream
git switch main
git merge upstream/main
git push origin main
```

GitHub画面ではForkページの `Sync fork` でも可能。

## 使い分け

| 目的 | 方法 |
| --- | --- |
| 作業Branchの完成分を原本へ戻す | PR -> Merge |
| 変更を数個だけ原本へ入れる | git cherry-pick |
| 原本の最新を作業Branchへ反映 | git merge main または git rebase main |
| Fork元の更新をForkへ取り込む | Sync fork / fetch upstream -> merge |
| 自分の修正をFork元へ提案 | Pull Request |

部分反映をするなら、最初から機能単位で小さくCommitを切る。

## ゲームのセーブとの対応

Gitはゲーム全体のセーブデータではなく、変更履歴を積み重ねるセーブ・ロード機能。

| ゲーム感覚 | Git |
| --- | --- |
| セーブスロット | Branch |
| セーブした瞬間 | Commit |
| セーブ内容のメモ | Commit message |
| セーブから再開 | git switch Branch名 |
| 成功データを本編へ採用 | Merge |
| セーブの一部だけ本編へ採用 | cherry-pick |
| 本編の最新状態を作業中データへ反映 | merge main |

```text
main                 動く原本・公開候補
feature/battle-ui    バトルUIの作業セーブ
feature/save-system  セーブ機能の作業セーブ
experiment/ai-enemy  敵AIの実験セーブ
```

Gitは「全部のセーブ地点を持つ分岐シナリオ帳」に近い。

## 用語定義

| 用語 | 開発での役割 | 使う場面 |
| --- | --- | --- |
| main | 原本・公開候補。常に起動できる状態 | 完成・検証済み変更だけ置く |
| Branch | 原本から分ける作業ルート | 自分のゲームに機能追加・修正・実験 |
| Fork | 他人のリポジトリを自分の管理下へ複製 | 外部OSSを改造、本家へ提案 |
| Commit | 変更の小さな保存単位 | 一段階が単独で意味を持つ時 |
| PR | 原本へ採用するための確認票 | Branchをmainへ戻す前 |
| Merge | PRで承認した変更を原本へ統合 | テスト済み・採用決定後 |
| cherry-pick | 特定Commitだけを別Branchへ複製 | 一部機能だけ先に採用 |

## 例題: 毒状態を追加する

### 1. 原本からBranchを作る

```text
main
└ feature/status-poison
```

```bash
git switch main
git pull
git switch -c feature/status-poison
```

このBranchでは毒状態だけを扱い、バトルUI作り直しや別モンスター追加は混ぜない。

### 2. 機能単位でCommitする

```text
feature/status-poison
├ 01: 毒状態のデータ定義
├ 02: ターン終了時の毒ダメージ
├ 03: 毒アイコンの表示
└ 04: テスト追加
```

```bash
git add src/data/statuses.ts
git commit -m "feat: add poison status definition"

git add src/battle/resolveTurn.ts
git commit -m "feat: apply poison damage at turn end"

git add src/ui/StatusIcon.tsx
git commit -m "feat: display poison status icon"

git add tests/poison.test.ts
git commit -m "test: cover poison turn damage"
```

### マージのルール

| 判定 | mainへ入れるか | 処理 |
| --- | --- | --- |
| 起動できる | 必須 | 起動不能なら入れない |
| 既存バトルが壊れていない | 必須 | テスト・手動確認 |
| 仕様が決まっている | 必須 | 未決定なら実験Branchに残す |
| UIまで完成 | 必須ではない | 機能価値が成立すれば可 |
| Debugコード・仮素材 | 原則不可 | 削除・分離してから |
| 他機能と無関係 | 望ましい | 混ざっていれば分割 |

### 完成分だけ採用する

毒ダメージまでを採用するならCommit 01と02をcherry-pickする。または最初から `feature/status-poison-core` と `feature/status-poison-ui` を分ける。

### Forkを使う例

外部の `battle-kit` に毒処理が足りない場合。

```text
作者: battle-kit
       ↓ fork
自分: shunsuke-k/battle-kit
       ↓ branch
      fix/poison-timing
```

自分のゲームだけで使うならForkを依存先にする。本体にも修正してほしいなら元作者へPRを送る。

## 実用ルール

- main: 動く原本。直接編集しない。
- branch: 依頼・機能・修正単位で作る。
- commit: ひとつ戻しても困らない小ささで保存する。
- PR: mainへ入れる前に作る。
- merge: 動作確認と仕様確認済みだけ。
- fork: 他人の原本を改造する時だけ。

月3本制作を想定する場合、各ゲームは原則として自分のリポジトリ内のBranch運用で十分。Forkは外部ライブラリを直す必要が出た時だけ使う。
