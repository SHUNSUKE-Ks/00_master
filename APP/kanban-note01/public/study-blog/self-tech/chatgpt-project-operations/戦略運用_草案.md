# Web ChatGPT Project / 戦略運用草案

> 状態: カンバン判断待ち。

## 判断

Web ChatGPTは、ローカルコードを常に読める実装環境として使わない。

代わりに、思い付き、企画の前段、背景、狙い、比較、ゴール、評価基準を蓄積する「戦略室」に寄せる。

```text
Web ChatGPT Project
  -> 背景 / ゴール / 選択肢 / 企画 / 評価 / 採用判断

Local Codex + Git
  -> 現在コード / 実装 / テスト / ビルド / Report
```

## Projectの単位

Projectは「作品ごと」または「長く続く開発領域ごと」に作る。

```text
Project候補
├ 作品: カプセルモンスター
├ 作品: VacareNote
├ 作品: PlotNest
├ 領域: SolidJS基盤研究
├ 領域: NovelEngine
└ 領域: 制作戦略 / 商品化
```

短い調査や一回限りの質問はProject外で行い、採用した結論だけをProject資料へ移す。雑談を全部Projectへ積むと、背景と決定が埋もれる。

## Project内の4層

| 層 | 置くもの | 役割 |
| --- | --- | --- |
| 指示 | 目的、話し方、判断基準、禁止事項、出力形式 | 新規Chatへ共通適用する方針 |
| ナレッジ | 概要、仕様、用語、判断ログ、現在の論点 | AIが戦略判断で参照する資料 |
| Chat | アイディア、比較、計画、レビュー、採用前の議論 | 作業ログ |
| Git / Codex | 実コード、履歴、Issue、検証、Report | 実装の正本 |

## ナレッジに置く最小セット

```text
project_overview.md       目的・対象者・今回のゴール
strategy_context.md       背景・なぜ今やるか・制約
decision_log.md           採用 / 保留 / 却下と理由
current_questions.md      今考えるべき論点
glossary.md               独自用語・ID・tag
handoff_schema.md         Codexへ渡す時に満たす項目
```

コード全体をProjectへ重複アップロードするより、「判断に必要な要約」を置く方が安定する。

## Gitパスの扱い

`C:\00_master\APP\...` やGitHub URLをProject資料に書いても、それは場所の案内である。Web ChatGPTがローカルファイルを自動で読めるようにはならない。

実装状況が必要な時は、以下のどれかを行う。

1. Codexへ実装依頼を渡し、対象リポジトリを読ませる。
2. Web側では、GitHub連携などで必要な公開/接続済み資料を明示して読む。
3. `project_overview` や `current_status` の要約をProjectナレッジへアップロードする。

Projectは同じProject内のchat、file、instructionを文脈として扱うが、「毎回すべてのファイルを完全に丸読みする正本」ではない。重要な決定や最新状態は、短い資料へ明文化する。

## Web側で話すこと

- 作品やアプリのゴール
- ユーザー、利用場面、価値
- 企画案の比較と採用条件
- 世界観、ゲーム性、情報設計
- 技術を採用する理由と非採用理由
- 成果を測る評価関数、KGI、KPI
- Codexへ渡す前に埋めるべき要件

## Codex側で話すこと

- 現在のファイル構造と実装状況
- 影響範囲と実装手順
- コード変更、テスト、ビルド、PWA、deploy
- 実際のエラーと再現手順
- Harness Reportと成果物パス
