# 資料: よいデザインとは何か／AI が判定できる基準の作り方／「型で決める」か「観察で育てる」か

- 作成: 2026-09-28（メインチャット・Opus）
- 目的: UI の見直し（Loop）を回す前に、「何をもって良いとするか」を考えるための勉強資料。Gemini などで脱線しながら読めるよう、各章の終わりに「問い」を置いた
- 前提: いま作っている Note Story（kanban-note01 V2.1）と、これから作るアプリ（KeyDeck・CGA01 ほか）の両方に使う

---

## 0. 先に結論

1. **よいデザインは1つではない。「目的 × 文脈（端末・状態・慣れ）× 負担の少なさ」で決まる。** だから判定基準は目的別に作る
2. **AI に判定させるなら、基準は「観察できる・1つだけ・合否が決まる・確かめ方つき」で書く。** 「センス」は判定できない
3. **「型（XState の状態・UI の種類）で決める」と「使う人の制作の流れを観察して育てる」は、どちらか一方ではなく組み合わせる。** 型が器、観察が中身。始めるなら、軽い観察（操作の記録）を先にして、型はそこから決める方が外れにくい

## 1. よいデザインとは何か

### 1-1. いちばん土台になる定義
国際規格 ISO 9241-11 は使いやすさ（ユーザビリティ）を次の3つで定義している。

| 観点 | 意味 | このアプリでの例 |
|---|---|---|
| 有効さ | 目的を達成できるか | 会話ログにセリフを書き切れるか |
| 効率 | 少ない手間・時間でできるか | Alt+数字で話者を1手で出せるか |
| 満足 | 気持ちよく使えるか | 書いている途中で邪魔されないか |

大事なのは「**決められた利用者が、決められた状況で**」という条件がつくこと。スマホで電車の中で書く人と、PC で集中して書く人では、正解が変わる。

### 1-2. 古典的な原則（判定の「ものさし」の元になる）

**ニールセンの10の原則（ヒューリスティック）** — UI 点検で一番よく使われる
1. いまの状態が見える（保存済み・送信中・録音中）
2. 現実の言葉に合わせる（専門用語より日常の言葉）
3. 利用者が操作を取り消せる（戻る・ごみ箱）
4. 一貫性（同じ見た目は同じ動き）
5. 失敗を起こさせない（危ない操作の前に確認）
6. 覚えさせずに見せる（候補を並べる）
7. 慣れた人には近道（ショートカット・テンキー）
8. 余計なものを出さない
9. 失敗したとき、原因と直し方を出す
10. 助け（ヘルプ）を用意する

**ノーマンの考え方（『誰のためのデザイン？』）**
- 手がかり（押せそうに見える）、反応（押したら何か起きたと分かる）、対応（ボタンの位置と結果が素直に対応する）、制約（間違った操作をできなくする）、正しい思い込み（利用者の頭の中の仕組みと実際が合う）

**数で言える法則**
| 法則 | 中身 | 判定への使い方 |
|---|---|---|
| フィッツの法則 | 遠くて小さい的ほど押しにくい | よく押すボタンは大きく・近く |
| ヒックの法則 | 選択肢が多いほど迷う時間が増える | 1画面の選択肢を絞る・分ける |
| ドハティのしきい値 | 反応が約0.4秒を超えると流れが切れる | 押してから0.4秒以内に何か反応を出す |
| テスラーの法則 | 複雑さは消えない。誰が引き受けるかだけ | アプリ側で引き受けて、利用者を楽にする |
| ヤコブの法則 | 人は他のアプリと同じ動きを期待する | 長押し・スワイプの意味を一般の約束に合わせる |

**数で決まっている目安**
- 押せる大きさ: Apple は 44pt 以上、Android（Material）は 48dp 以上、Web の規格 WCAG 2.2 は最低 24px（推奨 44px）
- 文字の見やすさ（明暗の差）: WCAG で 普通の文字 4.5:1 以上、大きい文字 3:1 以上

### 1-3. 「作るための道具」ならではの考え方
Note Story は、読むアプリではなく**作るための道具**。ここには別の原則が効く。

- **流れ（フロー）を切らない**: 集中しているときに邪魔が入ると戻るのに時間がかかる。「入力中に勝手に開く・フォーカスを奪う」は道具として最悪の部類
- **入口は低く、天井は高く、壁は広く**（Papert・Resnick）: 初めてでも使える／慣れると速い／いろいろな作り方ができる
- **モード（状態）の功罪**: 「モードがあると押し間違いが起きる」（Tesler の "No modes"）一方、「その場面で使える操作だけにする」と迷いが減る。**モードを使うなら、いまどのモードかが常に見えること**が条件（→ 3章の XState とつながる）

### 1-4. このアプリで、すでに見つかった「よい／悪い」
この数日の指摘は、そのまま基準の元になる。

| あったこと | 当てはまる原則 | 基準の芽 |
|---|---|---|
| Android でサイドバーが開き直し続けて書けなかった | 流れを切らない・利用者が操作を握る | 入力中は候補パネルを自動で開かない（印を付けるだけ） |
| 端末のポップアップ（prompt/confirm）が出ていた | 一貫性 | 確認はアプリの中のダイアログで。危ない操作は赤 |
| 入力欄が1文字ごとに外れた（プロット） | 流れを切らない | 打っている欄は作り直さない |
| 押す＝開く／長押し＝タグ を一度逆にして戻した | ヤコブの法則・一貫性 | 押す＝主な操作、長押し＝もう一つの操作。全画面でそろえる |
| 起動ページを作品一覧にした | 目的に合わせる | 起動したら、いちばん多い作業の入口 |
| テンキーの9グリッド・記号キー | 慣れた人への近道・覚えさせずに見せる | 近道は画面にも見えるボタンと対応させる |
| 画像を localStorage に入れて数枚で満杯 | 失敗を起こさせない | 容量の限界に先に当たらない作りにする |

## 2. AI の検証に使える判定基準の作り方

### 2-1. なぜ「センス」では AI が判定できないか
- 「見やすいか？」と聞くと、AI は毎回違う答えを出す（ばらつき）。長い説明を良いと思いやすい、先に見たものを良いと思いやすい、などの癖も知られている（LLM を審査員に使う研究で報告されている）
- だから **AI に渡すのは「感想」ではなく「合否が決まる問い」** にする

### 2-2. よい判定基準の6つの条件
1. **観察できる**: 画面・動き・数値で確かめられる（×「使いやすい」 ○「押してから0.4秒以内に反応が出る」）
2. **1つのことだけ**: 2つ混ぜない（×「大きくて分かりやすい」）
3. **合否が決まる**: はい／いいえ、または段階ごとの見本つき
4. **いつの話か書く**: 目的・端末・状態（「スマホ縦で、入力中は」）
5. **なぜかを書く**: 元になった出来事・原則
6. **確かめ方を書く**: 誰が・何で・どう見れば合格か

### 2-3. 確かめ方の3段階
| 段階 | 何で確かめる | 例 | 担当 |
|---|---|---|---|
| L1 数で測る | 自動の計測（ブラウザで寸法・色を測る、アクセシビリティ検査） | 押せる所は 44px 以上／文字の明暗差 4.5:1 以上／横にはみ出さない | 機械（Sonnet がテストを回す） |
| L2 動きを試す | 自動テスト（押す・打つ・戻る を再現） | 記号キーを押してもカーソルが外れない／Esc でダイアログが閉じる／入力中にパネルが開かない | 機械 |
| L3 見て判断 | 見本（よい例・悪い例）と照らして AI が判定、割れたら人 | 主なボタンは1画面に1つ／見出しの大小がはっきりしている | AI ＋ 人 |

**L1・L2 に落とせる基準を増やすほど、Loop（Sonnet）で安定して回る。** L3 は、見本を文字にして添え、2回判定して割れたら人（あなた・Opus）に上げる。

### 2-4. 基準1件の書き方（案）
```yaml
id: write-001
目的: 書く
いつ: スマホ縦・タブレット縦、本文の入力中
基準: 入力中は、候補のパネルを自動で開かない（合うアイコンに印を付けるだけ）
なぜ: 2026-09-27 Android でサイドバーが開き直し続けて書けなかった（流れを切らない）
確かめ方:
  段階: L2
  手順: スマホ幅で 柱： の行に入る → パネルが開いていないこと、Scene のアイコンに印があること
  合格: パネルが閉じたまま、かつ印がある
重さ: 高（書けなくなる）
よい例: [desk-mobile-hint]
悪い例: [android-sidebar-loop]
出どころ: 利用者の指摘（2026-09-27）
状態: 採用   # 候補 / 採用 / 保留 / 却下
版: 1
```

### 2-5. 集めて基準に変える流れ
1. **集める**: よい／悪いと思った画面（スクショ・URL）と、**あなたの一言（どこが・なぜ）**
2. **文字にする**: 画像は残らないので、すぐ「部品カード」（目的・端末・場所・大きさ・動き・なぜ）にする
3. **束ねる**: 同じ目的のカードが2〜3枚たまったら、共通点を「〜のときは〜する」の候補にする
4. **採用を決める**: 候補はあなたが 採用／保留／却下 を決める（判定の軸を決めるのは人）
5. **確かめ方をつける**: L1〜L3 のどれで確かめるか。書けない基準は判定に使わない
6. **Loop で当てる**: Sonnet は採用済みの基準だけで点検する。基準に無い気づきは「候補」として書き残す
7. **育てる**: あなたが「これは違う」と直したことは、新しい基準か悪い例として 1 に戻す。外れてばかりの基準は下ろす

### 2-6. 落とし穴
- **増えすぎ**: 目的ごとに大事な10件までに絞る。残りは「参考」
- **ぶつかる**: 「すぐ候補を出す」と「入力中は開かない」は目的と状態で優先を決める（だから目的別・状態別に書く）
- **測れる物だけ良くなる**（グッドハートの法則）: 数で測れる基準ばかりだと、測れない良さが削られる。L3 と、3章の観察で補う

### 2章の問い（Gemini へ）
- UI の点検基準を、自動テスト（寸法・色・操作）に落とす実例やツールを、Web アプリ向けに教えて
- AI（大規模言語モデル）に画面のスクショを見せて UI を採点させるとき、ぶれを減らす方法は？（見本の出し方・採点表の作り方）
- 判定基準が増えすぎたとき、優先順位のつけ方の定番は？

## 3. 「型で決める」か「観察で育てる」か

### 3-1. A: 型から最適解を決める（上から）
- **XState（状態の図）**: 画面や作業を「状態」に分け、状態ごとに使える操作を決める（メモ「XState で操作を状態ごとに限定する構想」）。元は Harel の状態図（1987年）
- **UI の型**: 一覧と詳細／入力／候補から選ぶ（パレット）／確認／段階を踏む入力 など。型ごとに定番のよいやり方がある（Apple・Google の指針、パターン集）

| よい所 | 弱い所 |
|---|---|
| 「状態 X では操作 Y だけ」と書けるので、AI が判定しやすい | 実際の使い方とずれることがある |
| 状態図から操作の道筋を作って、自動テストにできる | 型に無い「創作の動き」を拾えない |
| 新しい画面にもそのまま当てはめられる | 先に作る手間が大きい |
| モードがはっきりする | モードを見せないと押し間違いが増える |

### 3-2. B: 使う人の制作の流れを観察して育てる（下から）
アプリの中で「どの画面・どの状態で・何を・どうやって（キー／タップ／長押し）・どれくらいの間で」操作したかを記録し、そこから近道（コマンド）と並べ方（レイアウト）を作る。

- **見つけたいもの**
  - よく続けて使う操作の並び → 1つのコマンド（まとめ操作）にする
  - 行ったり来たり（パネルを開いて閉じてまた開く） → 並べ方を変えるサイン
  - 押した直後の取り消し → 押し間違いやすい所
  - 長く止まっている所 → 迷っている所
  - 一緒に使うパネル → 隣に置く
- **記録の形（案）**: 本文は記録しない。操作だけ
  ```json
  { "t": "2026-09-28T10:02:11Z", "screen": "desk", "state": "書く:柱の行", "action": "desk.tag.scenes", "via": "longpress", "device": "phone-portrait", "undoWithin5s": false }
  ```

| よい所 | 弱い所 |
|---|---|
| 実際の使い方に合う（あなた専用の最適） | たまるまで時間がかかる |
| 基準の根拠（データ）になる | 今の癖を固めるだけになることがある |
| 「どこで困っているか」が数で見える | 読み取り（解釈）に人の判断が要る |
| | 記録と保存の仕組みを作る手間、中身を残さない配慮 |

### 3-3. 結論: 組み合わせる（型が器、観察が中身）
- 観察の記録に「いまの状態（型）」を入れると、記録が意味を持つ（「書く:柱の行 で Scene を長押しが多い」）
- 観察で見つけたパターンを、状態ごとのコマンド・並べ方に落とし、よく効いたものを判定基準に上げる
- 状態の型は、**観察で分かってから決める方が外れにくい**。先に細かい状態図を描くと、使わない状態まで作ることになる

**このアプリは、観察を始める部品をもう持っている**
- キー入力モニター（キーを見る）
- ショートカットの登録と操作の名前（`desk.tag.cast` など。操作に名前がある＝記録しやすい）
- 画面の名前（route）と、行の種類で候補を切り替える仕組み（CANDIDATE_HOOKS ＝ ほぼ「状態」）

だから、次の順がいちばん軽い。
1. 操作の記録を軽く始める（本文なし・この端末だけ・止められる）
2. 2週間ほどためて、上の「見つけたいもの」を見る
3. 見つかったものをコマンド・並べ方にし、効いたものを基準へ
4. 状態が増えて込み入ってきたら（新しいアプリなど）、そこで XState で型にする

## 4. 全体のつながり（まとめ）

```
観察（操作の記録）
   ↓ パターンを見つける
コマンド・並べ方の案  ＋  判定基準の候補
   ↓ あなたが採用を決める
状態（型）ごとの判定基準（L1 数・L2 動き・L3 見本）
   ↓ Loop（Sonnet）で点検・直す
画面が変わる
   ↓ また観察して、効いたか確かめる
```

- **よいデザインの定義**（1章）が、基準の「なぜ」になる
- **判定基準の書き方**（2章）が、AI に任せられる範囲を決める
- **型と観察**（3章）が、基準の元（根拠）を増やし続ける
